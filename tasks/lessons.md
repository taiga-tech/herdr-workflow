# 教訓

- 永続参照用の文書には、特定の作業回を前提にした報告や移管時だけの説明を混ぜない。履歴は履歴専用の記録へ分離し、現行文書には現在の契約、状態、検証方法を書く。
- 文書の成熟度と製品の実装状態を同じ`status`で表さない。`draft`でも部分実装はあり得るため、実装状態はコードと試験結果で確認する。
- 文書チェッカーの対象を変更するときは、通常検査と監査用オプションの両方を実行する。保存ハッシュはGit履歴上の基準ファイルと照合してから修正する。
- 文書専用の検査・更新スクリプトは、リポジトリ共通の`scripts/`ではなく、担当するドキュメントスキルの`scripts/`に配置する。
- `.agents/skills`のスキルを`.claude/skills`から共有するときは、端末固有のFinder Aliasではなく、checkout間で再現できる相対symlinkを使う。
- リポジトリ内のPythonスクリプトはPythonを直接起動せず、`mise.toml`で固定したuvを経由して実行する。文書、スキル、検証報告のコマンド表記も同じ入口へ揃え、`python -B`で検査生成物を残さない。
- リポジトリ標準の検査コマンドは、内部のuv呼び出しを文書ごとに複製せずmiseタスクへ集約する。利用者向け文書とスキルは`mise run`を共通の入口にする。
- 「不要なファイル」の調査で文書名が例示された場合は、生成物監査だけで終えず、現行文書としての固有情報、旧パス互換、移行証跡、Git履歴で代替できるかを分けて評価する。
- 不要文書の整理を依頼された作業では、明示されていない整形設定へ変更を広げない。変更した文書だけを個別に整形し、通常検査と移行監査で保存資料への意図しない影響を検出する。
- serdeの`#[serde(tag = "type")]`で内部タグ付けしたenumでは、`deny_unknown_fields`は各バリアントの構造体アームではなくenumコンテナ自体に付ける(バリアントに付けると`unknown serde variant attribute`でコンパイルエラーになる)。`rename_all`はバリアント単位でもコンテナ単位でも有効なので混同しない。
- 文書追記後は`docs:test`/`docs:check`だけでなく`prettier --check`も必ず実行する。表の列幅がPrettierの折返し判定に影響するため、セル内容を長くする編集(未決事項の追記等)はフォーマット差分を生みやすい。
- serdeのderiveが標準で行う重複フィールド検出は、固定フィールド構造体(`#[derive(Deserialize)]`の構造体)には効くが、`BTreeMap<K,V>`型フィールドには効かない(`insert`が後勝ちで上書きするだけ)。重複キー検出が必要なmapフィールドには自作の`deserialize_with`ヘルパーが要る。新規crate追加を検討する前に、まずserde標準機能でどこまで賄えるか実験で確認する。
- `#[serde(tag = "type")]`の内部タグ付きenumは、serdeが内部で`Content`バッファ経由で再デシリアライズするため、その内側のフィールドで起きたエラーの行番号は不正確になる(enum値全体の外側の位置になる)。`serde_path_to_error`を追加しても同じ`Content`を経由するため改善しない。この制約はコードコメントと文書の両方に明記し、後から「行番号がおかしい」と誤診断されないようにする。
- 検証系のロジック(grid検証等)を作る前に、実際の設定例の値を手計算で確認しておく(今回はgrid配置のスライス可能性)。手計算で先に正解を出しておくと、実装のテストが「たまたま通った」のか「意図通り動いている」のか区別できる。
- rust-analyzerの型診断が保存済みコードの`cargo check`と食い違う場合は、診断行へ形式的な変更を加える前に、エディタの未保存バッファと保存済みファイルを比較し、VS Code拡張に同梱された同じrust-analyzerの`analysis-stats`でも再現するか確認する。保存済みコードとバッチ解析が正常なら、ファイル保存とlanguage server再起動で残留診断を更新する。
- `docs:test`は検査用にリポジトリ全体(`target/`を含む)を一時領域へ複製するため、Cargoが`target/`を更新している最中に並列実行しない。Cargo検査の完了後に文書検査を直列実行し、検証同士の競合を製品不具合と誤認しない。
- Herdr側のAPI・プラグイン仕様を確認するときは、ローカルにインストール済みのHerdr CLI(`herdr api schema --json`、`herdr --skill`が案内する公式docs URL)で実機確認できないか先に調べる。ヘルプに出てこないサブコマンド(`herdr plugin link`等)や、`herdr integration`のように名前が紛らわしく別機能を指すサブコマンドもあるため、ヘルプの見た目だけで「存在しない」「同じ機能」と判断しない。実機のSocket APIスキーマとバージョン固定した公開ドキュメント(タグ指定のGitHub raw URL)を突き合わせると、推測なしで仕様を確定できる。

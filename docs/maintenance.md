# 文書の更新と参照のルール

[文書目次](README.md) · [更新ルール](maintenance.md)

この文書の管理対象：参照先、ID、状態、更新単位、保管方法。

## 文書の分類

動作の規則を`specs/`と`reference/`へ、責務をアーキテクチャへ、操作手順を`guides/`へ、判断理由を`decisions/`へ分ける。[D1](reference/sources.md#d1)

一つの動作について、正式な参照先を一つに決める。機能一覧、目次、ADR、手順書には概要とリンクを置き、同じ既定値表や完全な設定例を別々に管理しない。機能一覧で見つけ、仕様で詳細を調べ、試験で期待結果を確認する。

## 文書IDとパス

各文書のfront matterに、安定した`id`、`title`、`status`、`documentVersion`、`updated`を記載する。`docs/manifest.json`は文書IDと配置先を一覧化する。IDは変更・再利用しない。ファイル名には章番号を付けず、話題を表す英語名を使う。

機能IDはF、試験IDはT、未決事項はQ、設計判断はADRを使う。本文の章順が変わってもIDは維持する。細かい参照には`<a id="...">`で置いたアンカーを使い、見出しの日本語表記変更に依存させない。[D3](reference/sources.md#d3)

文書を移動するときはmanifest、目次、相対リンク、章の移行表を同じ変更で更新する。すでに参照されている旧パスは、案内だけを記した文書として残す。廃止した仕様は状態と置換先を明示する。

## 状態の区分

| `status`    | 意味                                                       |
| ----------- | ---------------------------------------------------------- |
| `draft`     | 内容が未確定または非規範。実装状態はコードと試験で確認する |
| `proposed`  | ADRの判断案。利用者・保守担当の承認待ち                    |
| `accepted`  | 採用が確認され、実装と仕様の根拠にできる判断               |
| `current`   | 現在の文書目次、運用規則、履歴等                           |
| `reference` | 外部資料と、その確認範囲                                   |
| `redirect`  | 移動先への案内                                             |
| `archived`  | 過去資料の説明。現行仕様として使わない                     |

文書の採用状態、製品実装の完了、テストの実行結果は別に記録する。ソースコードの参照や実行結果がない状態で「実装済み」「対応済み」へ変更しない。文書の更新日は、その文書を実際に変更した日とする。

## 変更時の更新先

| 変更内容                   | 同じ変更で確認する文書                          |
| -------------------------- | ----------------------------------------------- |
| 新機能・範囲変更           | 機能一覧、対象仕様、受け入れ試験、実装段階      |
| コマンド・既定値・設定キー | 設定、CLI、設定例、運用手順、該当試験           |
| 構成・責務・永続化方式     | アーキテクチャ、ディレクトリ、対象仕様、新規ADR |
| 障害時の挙動・所有権       | 復旧、後片付け、承認、状態モデル、該当試験      |
| Herdr対応版・API           | Herdr連携、参考資料、互換性試験、未決事項       |
| 判断の撤回                 | 旧ADRの置換先、新ADR、現行仕様、CHANGELOG       |

ADRは一つの判断を一つのファイルへ記録する。採用後に方針を変える場合は過去の理由を消さず、旧ADRを新ADRで置き換えたことを残す。[D2](reference/sources.md#d2)

## 変更の確認手順

編集対象を目次で確認し、正式な参照先を更新する。影響する例、試験、関連ADRへ反映した後、次の検査を実行する。

```bash
mise run docs:check
```

この検査は文書構造の検査であり、製品仕様の正しさや製品試験の成功を証明しない。文書追加・移動時は`docs/manifest.json`も更新する。実行結果はCIや作業結果として記録し、現行仕様へセッション単位のログを追記しない。

## 継続的な保管と参照

文書をコードと同じGitリポジトリで管理する。PRでコードと仕様を同時にレビューし、リリースに対応する文書を同じcommitまたはtagで固定する。特定の時点を引用するときは、対象commitと文書IDを記録する。分岐名だけで過去の仕様を指したことにしない。

日常の参照には文書間の相対リンクを使う。Markdownファイルと設定例があれば参照できる構成とし、特定のチャットの履歴や外部の図表サービスを前提にしない。公開サイトを後から作る場合も、生成HTMLを手編集せずMarkdownを編集元にする。

作業計画、プロンプト、コマンドログ、レビュー過程、一時的な検証メモは`tasks/`等の作業領域へ分離し、README、仕様、リファレンス、ガイドには現在の契約と状態だけを書く。

## 元資料と外部資料

`archive/`の元資料は変更しない。元資料のハッシュと移行表を残し、当時の記述と現行仕様を区別する。外部資料は資料ID、確認日、対象版を記録し、未確認の機能を現在の事実として書かない。

## 文体と例

仕様は条件と挙動を明示する。推測、未決、設計提案、確認済みの外部仕様を区別する。製品の実装がない間は、例を現在使えるコマンドとして案内しない。pnpmとmiseの表記を維持し、実行対象プロジェクトの設定を勝手に追加しない。

## 履歴・監査資料

`CHANGELOG.md`、`archive/`、`docs/meta/`は履歴・監査資料であり、現行仕様の説明には使わない。移行や監査を明示的に行う場合を除き、これらへ作業ログを追記しない。

`mise run docs:audit`は、T01〜T32の記述を保存した基準スナップショットと照合する監査用タスクである。通常の文書更新では使用せず、仕様変更は主文書、試験、ADR、利用者に意味のある変更履歴へ反映する。

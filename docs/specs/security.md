## 実行承認と秘密情報

Herdrプラグイン自体はユーザー権限で動くコードである。[S2](../reference/sources.md#s2) 本設計の承認機構もOSレベルの隔離ではない。

初回の自動実行は無効とする。`trust`で、リポジトリ、設定ハッシュ、実行コマンド、コピー対象、Agent起動、ネットワーク利用等を確認して許可する。設定変更時には再承認する。非対話のevent経路では、未承認の処理に`holdReason=needs-approval`を付けて保留する。detached checkoutは`needs-branch`、イベントから決められない入力がある場合は`needs-input`で保留する。

<a id="approval"></a>

承認はリポジトリ(Gitの共通Gitディレクトリ。Gitリポジトリでなければ設定の場所)と設定ハッシュの組で記録する。設定ハッシュはworkflow設定の本文とプラグイン全体設定から計算し、本文を1文字でも変えると別の承認が必要になる。承認を必要とするのはイベント経路(`hook`)の自動実行であり、利用者がCLIで明示的に実行する`run`・`up`・`attach`には求めない。承認前に保留した受付は、承認後に同じイベントが届いたときに受け付け直す。

承認の成立条件([Q13](../planning/open-questions.md#q13))は次のとおりとする。

| 対象                     | 承認との関係                                                                                                                                                                         |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 設定本文とプラグイン設定 | 設定ハッシュに含める。変更したら再承認する([T25](../testing/acceptance.md#t25))                                                                                                      |
| Gitのhook・フィルター    | 承認時に表示した一覧の要約を承認と一緒に記録する。一覧が変わったら、設定ハッシュが同じでも`needs-approval`で保留する。状態ストア版4以前の承認は要約を持たないため再承認が必要になる  |
| 秘密値参照               | 参照する名前は設定本文に含まれるため設定ハッシュで変更を検出する。名前は承認時に表示する。値と`secrets.yaml`の取得元は利用者の管理下にあるため承認に含めない                         |
| 入力値                   | イベント経路で使うのは既定値と、イベントのブランチ名から渡す`branch`だけとする。既定値のない必須入力があれば値を推測せず`holdReason=needs-input`で保留し、`up`での明示実行を案内する |
| 実行計画ハッシュ         | 入力値で変わるため承認には含めない。Runごとに状態ストアへ記録する                                                                                                                    |
| checkout内容             | 承認に含めない。承認は設定と実行内容への許可であり、checkout内のコード(パッケージのscript等)を安全と判定しない                                                                       |

承認は許可項目ごとに分けず、上の条件を満たす一つの承認で設定全体の自動実行を許可する([Q09](../planning/open-questions.md#q09))。一部のタスクだけを承認して実行すると依存関係が途中で切れるため、部分的な承認は設けない。承認に有効期限は設けない。

`mise`やパッケージ管理ツールの信頼確認を迂回するフラグを自動で付けない。miseにも独自の信頼管理があるため、本プラグインの承認と同じものとは扱わない。[S11](../reference/sources.md#s11)

`pnpm install --frozen-lockfile`でも、プロジェクトや依存パッケージ由来の処理を実行する可能性を前提に承認する。実行する対象コードへの信頼は残る。設定ファイルの承認だけで、checkout内の任意コードを安全と判定しない。

`.env`をworktreeへコピーすると、そのworktreeを読むAgentも秘密値を読める。コピー許可とAgentへのアクセス許可を同時に説明する。認証情報を渡したくない場合はコピー対象から外し、タスク単位の秘密値参照を使う。

<a id="secrets"></a>

秘密値の実体は利用者の`$HERDR_PLUGIN_CONFIG_DIR/secrets.yaml`に置き、workflow設定には名前だけを書く。[設定](../reference/configuration.md#q11-keys) ファイルが現在の利用者の所有で、グループとその他の利用者が読み書きできない場合だけ読む。条件を満たさない場合は権限を変更せずエラーにする。Run開始時に参照した名前がすべて定義済みであることを確認し、未定義の名前があれば外部操作の前に失敗させる。値はAttemptの起動直前に読み直す。`fromEnv`はRunを要求したCLIの環境から読み、値が存在しなければ同様に失敗させる。CoordinatorはCLIから受け取った環境を状態ストアへ保存しない。

解決した値はログのマスク対象へ登録する。マスクは出力が値と完全に一致する部分に限られ、変換・分割された秘密値までは検出しない。承認と秘密値参照の関係は[承認](#approval)の表に従う。

Coordinatorの制御ソケット、状態ディレクトリ、結果ファイルは同じユーザーだけが利用できる権限にする。外部ネットワークへ制御APIを公開しない。送信者を検証しても、同一ユーザーの任意コードからの防御まで提供するとは扱わない。

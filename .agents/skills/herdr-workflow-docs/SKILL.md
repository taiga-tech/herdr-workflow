# Herdr Workflow の文書更新

現在の実装と採用済みの判断を、正式な参照先へ反映する。作業日誌ではなく、後の開発者が継続して参照できる契約と状態を残す。

## 更新前の確認

1. `AGENTS.md`、`docs/README.md`、`docs/features.md`を読む。
2. 変更差分、対象コード、関連テストを確認し、実装済みの挙動と設計案を区別する。
3. `docs/maintenance.md`の対応表から主文書を特定し、対象仕様、関連ADR、`docs/testing/acceptance.md`を必要な範囲で読む。
4. 本文、設定例、試験、ADRに食い違いがあれば、どれを正と判断したかを説明してから編集する。未決事項を推測で確定しない。

## 更新の原則

- 一つの仕様は一つの主文書で管理し、目次、機能一覧、ガイドには要約とリンクだけを置く。
- 現在の挙動はコードと試験結果を根拠に記載する。未検証の機能を「実装済み」「対応済み」と書かない。
- 設定例は`examples/workflow.yaml`を編集元とする。設定型や生成スキーマが存在する場合は二重管理しない。
- 採用判断や互換性を変える場合はADRと対象仕様を更新する。文書ID、機能ID、試験ID、論点ID、ADR番号は振り直さない。
- 作業計画、プロンプト、実行ログ、レビュー過程、一時的な検証メモをREADME、仕様、リファレンス、ガイドへ書かない。必要な作業記録は`tasks/`へ分離する。
- `archive/`と`docs/meta/`は過去資料と監査記録であり、明示的に移行・監査を依頼された場合を除いて更新しない。
- 日付や対象版は、外部仕様の確認範囲、互換性、リリースなど、将来の読者が根拠を判断するために必要な場合だけ記載する。

## 検証

リポジトリルートで次を実行する。

```bash
mise run docs:test
mise run docs:check
```

Rustコードを変更した場合は、`docs/guides/development.md`に記載された該当チェックも実行する。文書検査、Rustテスト、Herdr実機試験、実Agent起動は別々の検証として報告し、実行していない検査を成功扱いしない。
